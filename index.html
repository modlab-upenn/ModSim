Abstract. Physics engines such as MuJoCo, Isaac Sim and Gazebo treat a robot's structure as fixed, with no concept of modules, connectors, or the docking events that change which bodies are joined. Researchers simulating modular and self-reconfigurable robots therefore rebuild these concepts by hand for each platform and each engine, typically as one-off scripts that toggle constraints with no guarantee that the logical connection graph matches what the physics actually enforces. ModSim is a Python framework that makes modular-robot semantics a first-class, engine-independent layer. Robots are described once in a validated Robot Pack that adds modules, connector types, compatibility rules and acceptance tolerances to a standard URDF. At runtime, ModSim decides when connectors may dock, asks the physics engine to create the constraint, and commits the connection only after the engine confirms it, recording every change in a replayable event log. Physics engines plug in through a small adapter interface; a kinematic mock backend and a MuJoCo backend are available today.

Modular robots change shape while they run

Modular robots get their usefulness from changing topology at runtime: modules dock into assemblies, undock and rearrange. Engines like MuJoCo, Isaac Sim and Gazebo simulate a fixed assembly very well. A dock is different. It changes the mechanism mid-run, and the claim that two modules are now one assembly has to stay consistent with the constraint the engine actually enforces.

General-purpose engines don't represent that second half. MuJoCo can't add a joint on contact, so welds must come from a reserved pool. A logical connection must only count once the physical constraint exists. Docking rules are written between connector frames, while physics constraints are written between bodies. ModSim handles all of this once, in one place, for every robot and every backend.

What decides whether two modules dock?

Every connector type declares an acceptance region. Two connectors dock only when they are close enough, their docking axes point at each other, and they are closing slowly enough. Then ModSim asks the backend for the constraint and records the connection only after the backend confirms it. Try it: drag the teal module toward the blue one.

ModSim

Robot Packs. A self-contained folder: your URDF for geometry and kinematics, plus strict split-YAML for modules, connectors, compatibility, acceptance regions and docking policy. Packs are imported from URDF and edited in a desktop Studio, and validated before they ever reach a simulator.

Runtime and docking. Each step, the backend advances physics and reports poses, then ModSim resolves connector frames, releases overloaded or requested connections, and evaluates new docks. A connection is committed only after the backend confirms its constraint. State changes only through events, so the log fully explains every connection.

Backends and inspection. Adapters implement seven methods. The mock backend is kinematic and serves as the reference semantics. MuJoCo adds contact, gravity, effort-controlled joints, and runtime welds and hinges drawn from reserved pools. The Runtime Inspector shows live topology, events and planner decisions next to the native viewer.

Model views and planning. ModSim never stores a picture of the robot. Model views are immutable projections generated from the canonical state on demand: a topology graph of modules and connections, or a cubic lattice for systems like M-Blocks. Online planners publish their goals, routes and action progress alongside them, so you can see what the planner intends next to what the physics actually did. Try the playground below, then see the real Runtime Inspector recordings and step-by-step replays of real ModSim plans and runs.

Experiments

Every experiment ships with the repository and runs from one command. Videos are real-time unless marked.

SMORES-EP dock and undock

One module drives its pan face into a second module's rear face using differential wheel effort. The weld forms only once the measured face separation is under 1 mm, holds, releases after 80 ms, and the module reverses away.

SMORES-EP online self-assembly

Seven scattered SMORES-EP modules assemble into a target structure. An online planner assigns each module a goal, schedules parallel actions and plans routes, and the wheels drive every module into place under MuJoCo physics, with replanning when an approach stalls. The Runtime Inspector shows the plan, routes and action history alongside the 3D view.

M-Blocks planar reconfiguration

Six 3D M-Blocks cubes reconfigure from a rectangle into a line. Given only the initial and target shapes, the planner generates a sequence of lattice pivots; each cube spins up its flywheel, pivots about an edge hinge, and is checked on landing before the next move.

Findings

  • Semantics and physics never disagreed. The event sequence was exact: six initial dock/merge pairs, then four cycles of undock, split, dock, merge.
  • Physics owns all motion. After the initial placement, root pose, velocity and wrench writes are forbidden. Every movement comes from wheel effort and contact.
  • Capture is precise. In the two-module cycle, the weld formed with connector translation of about 1 mm or less at latch.
  • One pack, two backends. The same Robot Packs run on the mock and MuJoCo backends under one docking contract, checked by 537 passing tests with 86% branch coverage of the core.

Get started

Install from source and watch two modules dock. The quickstart walks through building a pack for your own robot.

git clone https://github.com/modlab-upenn/ModSim.git && cd ModSim
pip install -e ".[studio,mujoco]"
modsim run --gui examples/robot_packs/generic_cube \
  --fixed-connector front --moving-connector front --duration 4
