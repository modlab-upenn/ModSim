# Online planar planning

ModSim provides an experimental SMORES-EP online planner with two demonstrations:

```bash
modsim runtime examples/robot_packs/smores_ep --demo smores_online_assembly
modsim runtime examples/robot_packs/smores_ep --demo smores_online_driver_to_snake
```

Both launch the Runtime Inspector and MuJoCo companion. Use `--no-viewer` for
the Inspector alone. For headless execution with an optional final JSON frame:

```bash
python examples/scenarios/smores_online_planning.py --snapshot /tmp/planning-frame.json
```

The script also accepts `--demo smores_online_driver_to_snake` and `--duration`.
It exits unsuccessfully when the planner fails or the budget expires before
completion. The CLI supplies MuJoCo, gravity, ground, a 0.05 m initial height,
a 0.002 s step, and a 360 s simulation budget. `--speed` changes display pacing,
not physics or the controller. Programmatic `RuntimeInspectorConfig` callers
must specify the physical settings explicitly. The source checkout is needed
for the shared SMORES controller configuration in `examples/scenarios/`.

These are experimental planning demonstrations, not validated hardware motion
plans. Their terminal status and decision log report blocked routes, contact
alignment stalls, lost connections, and exhausted recovery attempts. Reaching
the display duration alone is not evidence of a completed assembly.

## Algorithm and provenance

The assembly layer implements root selection, planar unfolding, distance-based
assignment, and depth-group scheduling from Liu, Lin, Kim, and Yim,
[Parallel Self-Assembly with SMORES-EP (ICRA 2020)](https://www.modlabupenn.org/wp-content/uploads/2022/03/liu_smores_assembly_2020.pdf).
The [expanded journal paper](https://arxiv.org/pdf/2104.00800.pdf) supplies the
branch-count root criterion and the reconfiguration parallelization in §6.4.
The seven-module assembly goal and initial poses reproduce its Task 1 topology
and Table 1. Runtime geometry comes from measured pack connector frames, so
physical target poses and costs need not match the paper's ideal 80 mm cubes.

The graph root is a tree centroid: no connector branch contains more than half
the modules. The physical root is closest to the average XY location. With that
pair fixed, a deterministic Hungarian solver minimizes total straight-line
assignment distance. This cost does not include obstacles, controller dynamics,
or execution duration. Ties have deterministic ID/order resolution.

Actions at the same tree depth are candidates for concurrent execution. The
root's left/right face group precedes its pan/bottom group. Earlier groups must
commit and settle before dependent groups start. Paper TOP maps to pack `pan`.
Tree goals, unique connector use, a bijective fixed mapping, and distinct
unfolded target locations are checked before execution. Moving wheel-face
attachments requiring a helping module are explicitly rejected.

Driver-to-Snake accepts the existing benchmark's explicit module correspondence,
computes releases and new docking actions from initial/goal connector graphs,
and preserves already-correct bonds. It does **not** implement the 2019 paper's
general initial-to-goal graph correspondence search. The original scripted and
authored physical demos remain separate references.

All planner code is an original implementation in this repository. No external
research code, planner framework, or GUI dependency was added.

The five implementation stages map to these components:

| Stage | Implementation |
| --- | --- |
| Goal and observation models | `modsim.planning.models`: immutable, serializable planner inputs and snapshots |
| Assembly algorithm | `modsim.planning.assembly`: root choice, Hungarian assignment, depth groups, releases |
| Navigation and concurrency | `modsim.planning.routing`: bounded route search, swept footprints, timed reservations |
| Feedback execution | `modsim.runtime.online_planning`: scheduling, wheel control, capture, backoff, replanning |
| SMORES integration | Two runtime demos, headless runner, and the Inspector's Planning tab; connected-train execution remains experimental |

## Ownership and execution

`modsim.planning` contains immutable goals, assignments, actions, observations,
the assignment algorithm, and the route search. It imports neither Studio nor
MuJoCo. A goal is scenario input; it is not a Robot Pack schema extension.

`OnlineAssemblyScenario` owns scheduling and feedback. It reads measured poses
from `WorldState`, computes scoped efforts with `PhysicalDockController`, merges
them with braking/holding commands, and steps `RuntimeSession` exactly once.
Initialization is the only stage that can write root poses. Docking and release
always use the session lifecycle and backend confirmation. A completed plan
must match the requested committed connector topology.

Routes are generated by bounded space-time search over forward/reverse motion,
rolling turns, single-module pivots, and waits. Collision checks sweep the
rectangular footprint of every member of a moving assembly. Turns account for
the imported root-to-axle offset. Moving trains use an approximate assembly
drive center and rolling turns. Both the footprint profile and contact model
are provisional; this is not a dynamics feasibility or collision-freedom proof.

Reservations predict the remaining motion of active actions and hold their
terminal occupancy. Runtime motion also checks measured clearance ahead. The
final mating corridor excludes the intended receiving module and removes the
extra navigation padding so legitimate close-packed docking is possible; other
modules remain obstacles. Initial face-release padding can be escaped without
increasing its overlap. A free future participant blocking an approach can be
given an explicit clearance relocation before its docking dependencies are ready.

Routing/scheduling runs at a separate cadence from effort control. Search has
finite expansion and horizon bounds. Planning currently executes synchronously
in the simulation owner; physics does not advance during a search, so a result
cannot race a newer world sample. Costly searches can lower wall-clock speed.
Frames include sample, topology, and plan revisions for future asynchronous use.

The executor tracks progress, recomputes receiving connector targets, and
replans after target drift, tracking/alignment stalls, or rejected captures.
Failed approaches back away under wheel control before generating another route;
this recovery is visible as a `retreating` interval and a decision-log entry.
Recovery attempts and action execution time are bounded. Assignment stays fixed
during route recovery. Unexpected loss of a committed connection stops the plan
with a failure instead of silently treating the goal as achieved.

## Runtime Inspector

Online demos expose three Inspector tabs. **Runtime state** places live and
target topology side by side using the same node-and-edge renderer and stable
logical layout. Both use current assembly colors; target edges are dashed while
needed and green when committed. Planned edges never become live graph edges.

**Planning** contains:

- measured XY module outlines, heading indicators, and recent movement trails;
- dashed goal poses, generated routes, and footprint samples along those routes;
- per-action depth groups, current phases, dependencies, and waiting reasons;
- an **Action history** chart: one row per docking action, with colored segments
  showing time spent in each state using simulation timestamps;
- connector position, axis, and relative-velocity diagnostics for a selected action;
- plan revision, peak planning-cycle time, accumulated travel, replanning count,
  and action diagnostics.

**Event log** contains separate tables for canonical simulation events and planner
decisions. Both remain available when the run ends.

The history chart zooms and pans only along time. Module rows keep their height
and can be scrolled vertically without hiding the time axis. Hover a segment for
its state, start/end times, and duration. **Follow time** keeps the whole run in
view; manual time navigation turns it off so incoming updates preserve the chosen
range. **Fit all** restores the full time range. The divider above the chart
resizes it independently of the workspace. Every graphical view has a collapsible
legend; hovering its legend control provides the same explanation.

Paths and goal poses can be hidden independently. Theme switching and manual
camera ranges are preserved. Pause/Resume/Stop control the same authoritative
simulation as the MuJoCo window. Planner intent is an optional immutable field
in `RuntimeInspectorFrame`, separate from generated world views and canonical
events. IPC protocol version 2 carries the extended frame; parent and companion
must use the same installation. Old version-1 peers are explicitly rejected.

Interactive runs stop advancing on a terminal scenario result. **Target reached ·
Simulation complete** appears only after the planner reports completion. Failures,
manual stops, and a time limit reached before completion have distinct banners.
The Inspector and native viewer retain the frozen final result for inspection;
completion disables playback controls. The direct `RuntimeInspectorRunner.step()`
API still permits additional steps for physical hold/validation experiments.

## Validation and limits

The maintained focused tests check the published assignment and parallel groups,
Hungarian costs against exhaustive small assignments, topology/helper validation,
fixed-mapping reconfiguration, swept assembly collisions, timed reservations,
bounded search failure, physical single and parallel docking without root writes,
recovery after an injected backend capture rejection, coherent world-sample stamps,
frame serialization, and the native planning widget across all three themes.

Run them with the relevant optional dependencies installed:

```bash
pytest tests/test_planning.py tests/test_online_planning.py \
  tests/test_runtime_planning_widgets.py
```

The seven-module paper assembly has completed in headless MuJoCo in approximately
328 simulated seconds with four replans. This is an observed integration result,
not a completion guarantee across solver versions or arbitrary layouts.
The connected Driver-to-Snake implementation currently remains a debugging case:
multi-module train tracking and crowded approach clearance can exhaust its
recovery/time bounds before the snake is formed. Search failure reports its
bounds and is not a mathematical proof that the task is impossible. Helper
lifting, loop closure, arbitrary 3D goals, general 2019 graph correspondence,
perception/SLAM, arbitrary scene-obstacle import, and hardware execution remain
outside this implementation.
