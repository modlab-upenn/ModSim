Quickstart

Simulate your own modular robot

This guide takes you from a URDF of one module to a script where several of them find each other, dock, and come apart again. Each step builds on the last, so it reads best in order.

Time about 45 minutes You need Python 3.11+ and a URDF of one module Example a module called my_module in a pack called my_robot

The five ideas you need

ModSim adds a few concepts that a physics engine doesn't have. Every step below is about one of them.

Module
One physical unit of your robot, described by one URDF. A system is many copies of one or more module types.
Connector
A spot on a module where it can attach to another module: a magnetic face, a latch, a hinge port.
Connector type
The shared rules for a kind of connector: what it can mate with, how precisely two must line up, and what joint forms when they do.
Robot Pack
A folder holding your URDF plus a few YAML files that describe your modules and connectors. It's the only thing ModSim needs from you.
Assembly
A group of modules that are currently connected. A module on its own counts as an assembly of one.

ModSim decides whether two connectors should dock and keeps track of what's connected. The backend handles the physics. You'll use two: mock, which has no physics and answers instantly, and mujoco.

1Install ModSim

ModSim isn't on PyPI yet, so install it from a clone of the repository. The mujoco extra adds physics and the 3D viewer. The studio extra adds the desktop editor and the Runtime Inspector.

git clone https://github.com/modlab-upenn/ModSim.git
cd ModSim
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e ".[studio,mujoco]"

Check that both backends are available:

modsim backends

Prefer uv? Run uv sync --extra studio --extra mujoco, then put uv run in front of each modsim command.

2Turn your URDF into a Robot Pack

Your URDF stays the source of truth for shape, mass and joints. ModSim copies it, with its meshes, into a new self-contained folder, then you add the modular parts on top.

modsim pack init --from-urdf path/to/my_module.urdf --out packs/my_robot

You get this folder:

packs/my_robot/ robot_pack.yaml the manifest: names the pack, lists every file specs/ module_types.yaml your modules and where their connectors are connector_types.yaml the rules for each kind of connector capabilities.yaml actions a module can perform, such as dock mappings/ urdf_mapping.yaml links URDF names to pack names assets/ urdf/ meshes/ your copied URDF and meshes

Run modsim pack inspect packs/my_robot to see what was imported, including the module ID the importer chose. This guide calls it my_module.

TipIf you use Xacro, expand it to a plain .urdf first. If the importer can't find your meshes, point it at their folder with --asset-root path/to/meshes.

From here you can edit the YAML files directly or open the pack in Studio with modsim studio packs/my_robot. Studio edits the same files, and the steps below say where each setting lives in both.

3Decide how your connectors mate

Before placing any connectors, describe the kind of connector your hardware uses. If every face of your module is the same magnetic face, you need one connector type. If you have, say, a male latch and a female socket, you need two.

Here's a hermaphroditic magnetic face that can attach at four rotations:

specs/connector_types.yaml
schema_version: "0.1"
connector_types:
  magnetic_face:
    name: Magnetic Face
    active: true
    gender: hermaphroditic
    compatible_with: [magnetic_face]
    allowed_orientations:
      mode: discrete
      values_rad: [0.0, 1.5708, 3.1416, 4.7124]   # 0°, 90°, 180°, 270°
    acceptance_region:
      shape: box
      position_tolerance_m: 0.006               # within 6 mm
      orientation_tolerance_rad: 0.14           # within about 8°
      max_relative_velocity_m_s: 0.05           # closing slower than 5 cm/s
    physical_connection:
      constraint: fixed
      compliance: null
    limits:
      max_normal_force_n: 90.0
      max_shear_force_n: 40.0
      max_bending_moment_nm: 1.8
    supports_undocking: true
    docking_policy:
      auto_latch: true                         # permanent magnets grab on their own

What each part decides:

gender, compatible_withWho can mate with whom. Male pairs with female, and hermaphroditic with hermaphroditic. Compatibility must be listed on both types, or ModSim treats the pair as incompatible.
allowed_orientationsThe rotations about the docking axis at which two connectors can join. Use continuous with an empty list if any rotation works.
acceptance_regionHow close, how well aligned, and how slow two connectors must be before a dock is accepted. If two types disagree, the stricter value wins.
physical_connectionWhat the physics engine creates on docking: fixed for a rigid weld, or hinge for a pivoting joint (add hinge.axis and hinge.anchor_separation_m).
docking_policyOptional. auto_latch: true docks as soon as the rules are met. Leave it false for connectors your robot has to actively engage, and request the dock in code. You can also set break_force_n so a connection releases under too much load.

In Studio: select Connector Types, then Add connector type. Turn on Declare docking policy to edit the policy fields.

4Put connectors on your module

Now say where each connector physically sits. A connector is attached to one link of your URDF, at a pose relative to that link.

specs/module_types.yaml
module_types:
  my_module:
    name: My Module
    asset_ref: my_module
    root_link: base_link
    mass_kg: 1.0
    connectors:
      - id: front
        connector_type: magnetic_face
        parent_link: base_link
        frame: null
        local_pose:
          xyz_m: [0.05, 0.0, 0.0]          # centre of the front face
          rpy_rad: [0.0, 0.0, 0.0]
        docking_axis: [1.0, 0.0, 0.0]      # points out of the face
        approach_axis: [1.0, 0.0, 0.0]
      - id: rear
        connector_type: magnetic_face
        parent_link: base_link
        frame: null
        local_pose:
          xyz_m: [-0.05, 0.0, 0.0]
          rpy_rad: [0.0, 0.0, 3.1416]
        docking_axis: [-1.0, 0.0, 0.0]
        approach_axis: [-1.0, 0.0, 0.0]
    capabilities: [dock, undock]

The one rule to remember: the docking axis points out of the connector, in the parent link's frame. Two connectors line up when their docking axes point straight at each other. Axes are unit vectors, and all distances are in metres.

The capabilities line refers to entries in specs/capabilities.yaml. Make sure dock and undock there list magnetic_face under required_connector_types.

In Studio: under Module Types → my_module → Links, select a link and choose Add connector to this link. Studio draws the connector in the 3D view as you type its pose.

5Make joints drivable (optional)

If your module has wheels or actuated joints you want to command, mark them in the module's joints list. MuJoCo creates a motor for every joint that declares effort control with a finite effort limit.

specs/module_types.yaml, inside my_module
joints:
  - id: wheel
    source_joint_name: wheel_joint      # the name in your URDF
    type: continuous
    parent_link: base_link
    child_link: wheel_link
    axis: [0.0, 1.0, 0.0]
    control_modes: [effort]
    limits:
      max_effort_nm: 0.8
      max_velocity_rad_per_s: 12.0

The importer fills in most of this from your URDF. You usually only add control_modes and check the limits. Effort is the only control mode MuJoCo runs today.

6Validate the pack

Validation catches mistakes before you simulate. There are two levels:

modsim pack validate packs/my_robot                        # while you're still editing
modsim pack validate packs/my_robot --profile simulation   # before you run it

The default level reports missing details as warnings. The simulation level turns them into errors, because a simulation needs them. Every problem names the file, the exact field, and often a suggested fix, and you get all of them at once. In Studio, press F6 and F7 for the two levels.

Heads upValidation checks that the pack is complete and consistent. It doesn't run physics, so a pack can pass and still fail to dock if, say, a docking axis points into the module instead of out of it. Step 7 catches that.

7Test docking without physics

This is the fastest way to check your connector setup. modsim dock places copies of your module in a row, already touching, and asks whether they would dock. It uses the mock backend, so it takes a second.

modsim dock packs/my_robot --count 3 --spacing 0.1

Set --spacing to your module's width so the faces meet. You'll see each pair that came close, which docked, and the resulting assemblies. Three modules docked front-to-rear should give you a single assembly.

If nothing docks, the report tells you why. Each pair was either never close enough, failed one of the acceptance rules (and which one), or was blocked by a policy rule. See When things don't dock for the common causes.

Add --undock to check that connections also release, or --no-latch to see what happens with only auto-latching connectors.

8Run it in MuJoCo

modsim run places two modules facing each other, drives one into the other along the connector's docking axis, docks them, and later pulls them apart. Name the connectors that should meet:

modsim run packs/my_robot --backend mujoco \
  --fixed-connector front --moving-connector rear \
  --undock-at 4 --duration 6 --gui

With --gui, two windows open on the same simulation. The Runtime Inspector shows the connection graph and every event as it happens. The MuJoCo viewer shows the bodies. Press Space in either window to pause both.

  • Use --view for just the MuJoCo viewer, or neither flag for a headless run.
  • Add --gravity --ground --height 0.2 to drop the modules onto a floor and let them settle first.
  • On macOS, run --view under mjpython instead of python.

9Write your own experiment

The commands above are scripted demos. For your own research you'll want to control the scene yourself. The pattern is always the same: load the pack, place modules, create a session, then step it and react to events.

experiment.py
from pathlib import Path

from modsim import RobotPackLoader, RuntimeSession, SceneSpec
from modsim.core import DockCommitted
from modsim.core.ids import ConnectorInstanceId

# 1. Load your pack
pack = RobotPackLoader().load(Path("packs/my_robot"))

# 2. Place two modules 10 cm apart along x (named my_module_0, my_module_1)
scene = SceneSpec.grid("my_module", count=2, spacing_m=0.1)

# 3. Start a session on MuJoCo (swap in "mock" to test logic without physics)
session = RuntimeSession.create(pack, scene, "mujoco", gravity=(0.0, 0.0, 0.0))

# 4. Ask for a dock, then step and watch what happens
session.request_dock(
    ConnectorInstanceId("my_module_0/front"),
    ConnectorInstanceId("my_module_1/rear"),
)
connection = None
for _ in range(500):
    for event in session.step(0.002):
        print(f"{session.world.time_s:.3f}s  {event.kind}")
        if isinstance(event, DockCommitted):
            connection = event.connection_id

# 5. Release the connection and read the results
if connection:
    session.request_undock(connection)
    session.step(0.002)
print(session.metrics().as_dict())
session.shutdown()

A few things worth knowing as you build on this:

  • Docks happen inside step(). A request is queued and checked against the rules on the next step. The dock only counts once the physics engine confirms the joint exists.
  • Events are your record. step() returns what happened in that step: candidates found, docks committed, assemblies merged and split. session.world holds the current state.
  • Custom layouts. Use SceneSpec.of([...]) with ModulePlacement entries to place modules at any pose.
  • Driving joints. Send torques with session.set_joint_commands([JointCommand(JointInstanceId("my_module_0/wheel"), ControlMode.EFFORT, 0.3)]). ModSim checks every command against your pack's limits before the backend sees it.

When things don't dock

Most first-time problems are one of these.

The connectors are never close enough

Check that xyz_m puts the connector on the module's surface, not its centre, and that --spacing matches your module's size. Studio's 3D view shows where each connector actually sits.

The pair fails axis_alignment

A docking axis is probably pointing into the module instead of out of it. Front and rear faces should have opposite axes, such as [1, 0, 0] and [-1, 0, 0].

The pair is blocked with command_required

At least one connector type has auto_latch: false, so ModSim waits for an explicit dock request. Call session.request_dock(...), or set auto_latch: true if your hardware latches on its own.

Two types that should mate are treated as incompatible

Compatibility must be declared on both sides: each type lists the other in compatible_with. Also check that the genders pair up (male with female, hermaphroditic with hermaphroditic).

A hinge connection works in MuJoCo but fails on the mock backend

This is expected. The mock backend refuses hinges on purpose, because it can't model rotation. Test hinge connectors with --backend mujoco.

After undocking, the modules stay stuck together

Releasing a connection doesn't push anything apart. The modules keep moving together until something drives them away, just like real hardware. modsim run backs the moving module off for you. In your own scripts, drive it away after the undock.
